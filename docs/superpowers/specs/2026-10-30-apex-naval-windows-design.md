# APEX Naval Command — Windows delivery design

Status: source reconnaissance and proposed implementation contract only; no product implementation or Windows acceptance in this document.

## Intent and authority

Deliver `APEX-NAVAL-COMMAND-Windows-x64.zip` for Windows 11 Pro x64. After extracting the whole archive, the user double-clicks `APEX-Desktop\ApexDesktop.exe`; no manual .NET, Node, Python, SDK or Visual Studio installation is required. Open the default browser automatically and keep all application listeners on **127.0.0.1 only**. Preserve the existing C# architecture, five Naval views, original Polish panel, optional lazy 3D, strategies, settings, risk controls, pairing and platform companions.

The current task writes design/plan only. Later implementation may use the request's scoped push/Actions authorization on `feature/apex-naval-command` in `kubson1995xx-cloud/bottt`; no merge/deployment is authorized. No real account connection and **no DEMO or LIVE transaction** is authorized. Presentation is synthetic/historical, not broker readiness, actual P&L or profitability evidence. No production simulation bypass, financial endpoint, automatic START, strategy promotion, AI Lab/training/LLM/updater or new broker integration.

Authoritative starting state: `fff4baf65cc4445c5630790b668fd0f713fab006`, `feature/apex-naval-command`. Read the current top of `HANDOFF.md` before implementation; its Windows resume supersedes historical permission/blocker entries. Other worktrees are out of scope. Existing Linux delivery and Task5A/UI/3D acceptance are not unfinished implementation tasks.

## Builder-owned choices

### 1. Keep one host and the existing publish/layout

Keep `net8.0`, assembly/executable name `ApexDesktop`, the current solution and `APEX-Desktop` directory. Keep self-contained single-file `win-x64` publish with `IncludeNativeLibrariesForSelfExtract=true`; explicitly disable trimming and ReadyToRun. Static `wwwroot` remains adjacent to the EXE. The ZIP is a portable folder distribution, **not a single-EXE-only promise**, installer, service or signed publisher release. The `.cmd` convenience launcher remains optional; documented primary entry is the EXE itself.

Add public synthetic `APEX-Desktop/presentation/naval-publication.json`, `APEX-Desktop/presentation/presentation.json`, `Weryfikacja/windows-publish.json`, and root `PRZECZYTAJ.md`. No other new payload subtree. Continue genuine runtime notices, cTrader `.algo` pair and optional MT5 source. Do not introduce WindowsDesktop/WPF/WinForms dependencies just to show startup instructions; use a small Win32 modal through P/Invoke.

`windows-publish.json` records actual publish argv, RID, SDK/runtime pack versions, unbundled intermediate runtimeconfig's `includedFrameworks` and file hashes. Both `Microsoft.NETCore.App` and `Microsoft.AspNetCore.App` must be included; shared `framework`/`frameworks` dependency is forbidden. Native proof launches the shipped EXE with empty DOTNET_ROOT/DOTNET_ROOT_X64, multilevel lookup disabled and no dotnet in its child PATH; inspect loaded runtime module locations to rule out borrowing the machine runtime. Build-tool SDK remains available to the parent test runner. Reject VC++ redistributable DLLs borrowed from machine installation too (for example `vcruntime140.dll`/`msvcp140.dll`); ordinary Windows OS components such as `ucrtbase.dll` are platform dependencies, not a promise to bundle Windows. Required non-OS native runtime DLLs must come from the authenticated publish/bundle, with native module-path proof. Missing dependency is a failed gate, not an instruction for the recipient to install it. Existing single-file extraction uses the .NET runtime's extraction mechanism; record/validate its per-user location and permissions in native tests, outside the sealed ZIP. If Windows publish emits additional required loose files, stop and approve an exact authentic file-set extension with tests; never broadly allow arbitrary DLLs/EXEs to get green.

### 2. Private data is a prerequisite, not a post-load repair

On Windows, resolve `--data` > `APEX_DATA_DIR` > `%LOCALAPPDATA%\APEX Trading AI`. Preserve that default for upgrade compatibility. Missing LocalAppData is an error, not an application-directory fallback. Explicit override must be fully qualified, local fixed-volume/ACL-capable, canonical and outside the **whole release root**, executable directory, webroot, source tree and any Naval authority directory. Reject UNC/device/ADS/relative/traversal paths, reparse components and files used as directories. Compare canonical path components case-insensitively, not string prefixes; resolve Windows 8.3/long-name aliases before containment. Case sibling `APEX-Other` must not be mistaken for child `APEX`.

Create each missing private directory with a native security descriptor **at creation**, current-user owner and protected DACL allowing only current SID, SYSTEM and Builtin Administrators, inheritable to files/subdirectories. No create-broad-then-chmod race. New files inherit that private parent. Validate existing directories/files recursively without following links **before config, lock, logs, accounts or publication access**. Existing unsafe trees fail closed with no ACL rewrite, deletion, credential reset, migration, config write or listener. This includes pre-existing nested files with explicit broad read grants and reparse descendants. Recheck directory identities through startup; hold directory handles without delete sharing for relevant ancestors/private root while bootstrapping, and validate target files around open to prevent rename/reparse substitution. Same OS user/admin remains trusted; this is not a sandbox against them or a power-loss guarantee.

Unify Windows path/ACL inspection with `NavalPrivatePath`; retain its stricter credential/leaf rules and Unix behavior. Distinguish object-effective ACEs from inherit-only ACEs. Private targets accept only trusted allow grants and trusted owner, reject null/absent DACL and unsupported/unprovable ACE forms. Ancestors can be readable/traversable and allow creation of unrelated siblings, but must not let an untrusted SID replace the protected child (DeleteChild, target modification, ACL/ownership changes). Recognize the native TrustedInstaller SID only for system-ancestor ownership, never as a new private-file principal. A typical Windows system root/User profile must work; do not exempt all of TEMP or weaken broad-file negatives to bypass a runner ACL failure.

Stable safe failure codes: `HOST_DATA_PATH_INVALID`, `HOST_DATA_PERMISSIONS_INVALID`, `HOST_DATA_UNAVAILABLE`; display Polish remediation with no secrets/raw exception dump. Preserve invalid existing bytes.

### 3. A usable first run without anonymous operator bootstrap

Windows-only initialization runs under the validated private root and exclusive `apex.lock`. Empty/new root gets profile `windows-local-presentation-v1`. Existing config/nonempty legacy data is **preserved**, including `NavalRead` off, custom ports, profiles, risk and STOP latches; no automatic migration/enrollment. Explicit `--data` empty roots use the same first-run policy. Linux/default source fixtures remain compatible and Naval off unless already configured.

New first-run private files (never shipped):

- `local-startup.json`: schema `apex-local-startup-v1`, profile, initialization state (`pending`/`ready`), presentation identity; no reusable secret.
- `private/local-access.json`: existing `naval-local-access-v1` with `operator`/`reader`, exact one scope `presentation`, independently random 32-byte canonical base64url secrets and lowercase SHA256 digests.
- `private/local-access.dpapi`: those local web credentials encrypted using Windows DPAPI **CurrentUser**; no machine scope. Needed to show the operator their generated credential again, not for web authentication. No broker keys.
- `publication/naval-publication.json`: private copy of the public build-time synthetic export.
- `apex.config.json`: existing HostConfig with zero real runtime accounts, NavalRead enabled, derived matching scope/paths, defaults 0.5%/1.5%/5%/5x and unchanged feature capabilities. New presentation profile disables automatic news fetching; existing settings are untouched.

Write a pending marker before other initialization, publish config last, then ready marker. Interrupted initialization is detected and fails `HOST_LOCAL_SETUP_INCOMPLETE`; never treat leftovers as clean state or regenerate credentials. All writes are private/atomic; preserve evidence and explain recovery. Existing ready marker with missing/invalid credentials also fails, never downgrades to legacy anonymous mode.

Use `WindowsLocalAccessPrompt` (Win32 MessageBoxW with OK/Cancel) to show local operator login/43-character generated password **only in the user's native modal**, never stdout/stderr/logs/files in plaintext, HTML/JS, browser URL, environment or command line. Tell the user to save it in their password manager and enter it into the browser's native Basic prompt. Do not automatically copy to clipboard. `--show-local-access` reopens this modal after the same private-path/DPAPI validation; it starts no host/listener/browser and never rotates existing credentials. Unavailable UI/DPAPI/cancel on initial setup exits safely with no listener; ready private state is retained for retry. Tests inspect the modal only in private memory and acknowledge it; never screenshot it or publish its text. This is local web access provisioning, not broker provisioning or financial authority.

For an enabled Naval host open `http://127.0.0.1:<port>/?view=naval`. This exact **nonsecret** root query gets the existing root-first Basic challenge; only after the same Operator policy succeeds does RenderIndex issue fixed relative `302 Location: /naval/`. `/` without that query remains the original Polish panel. No user-controlled redirect, query token, fragment credential, cookie/session auth, anonymous exchange endpoint or role grant. Reader/anonymous controls remain 403/401; no plaintext/digest credential in documents. A normal existing Naval-disabled config opens `/` and retains its historical mode rather than silently changing auth. Explain that legacy mode is not a reader-safe portal.

### 4. Real presentation, no production simulator

Generate public presentation during the existing builder from `tests/Apex.Backtester.Tests/fixtures/synthetic/naval-shared-replay-v1.json`, using the built `Apex.Backtester.dll naval-shared-replay` CLI and `--publication`. Authority, result and CLI logs stay in private build scratch. Ship **only** the validated export plus small `presentation.json` containing schema `apex-presentation-v1`, export SHA256, input/Core/Backtester SHA256 and derived `NavalRead.Scope`. Never synthesize a plausible export by hand, ship authority or execute the replay/exporter in the production host.

Runtime validates metadata and export with existing `NavalPublicationReader.Parse`, copies it into private publication storage only for initial setup, and uses the existing passive reader. A file update, restart or browser clock never makes it live. A stable historical checkpoint is enough for five views and optional 3D; hydration must not replay trading effects. No producer loop or simulation switch in Program, JSON, CLI or environment. Corrupt/missing presentation must fail safely instead of inventing empty balances. Existing configured-source failure remains HTTP503/UNKNOWN and the old panel/textual Emergency path still works.

### 5. Startup lifetime and browser

Order: resolve/validate/create private data → acquire lock → classify/initialize/load config → load auth/publication options → validate HTTP port (1..65535) → construct/map host → `StartAsync` HTTP bind → optional bridge/news startup → request default-browser shell open → `WaitForShutdownAsync`. Use using/try/finally for application/accounts/bridge/news/CTS/lock; configure stop cleanup before startup. No background financial activity or browser navigation before admission/bind succeeds.

HTTP-port collision: safe `HOST_HTTP_BIND_FAILED`, exit2, zero browser requests, no alternative-port search and no navigation to a stranger already on that port. Same-data second launch: `HOST_ALREADY_RUNNING`, exit2, no browser/config/credential mutation. Different-data/same-port also fails without opening a foreign panel. Stop/restart releases resources and preserves safety/config/publication bytes; restart never auto-STARTs. Optional TCP collision retains panel/WebSocket availability and clear degraded diagnostics.

Use `Process.Start(new ProcessStartInfo(url) { UseShellExecute=true })`, not preferred Edge/app-mode nor shell command concatenation. Fixed loopback URL only. Existing `OpenBrowserOnStart=false`/`--no-browser` remain supported. Shell-launch failure keeps the ready host available and shows a Polish nonsecret URL/instruction; report launch request versus actual browser navigation honestly. The default association is exercised natively; a separately launched Edge CDP proves served-panel behavior, not the user's chosen default-browser configuration.

## Proposed implementation boundaries / interfaces

All new types are internal under `Apex.Desktop.Services`; keep `Program.Main`'s production false authority.

- `WindowsPrivateData.Open(string requestedPath, string releaseRoot): WindowsPrivateDataLease : IDisposable`; `lease.Path`, `lease.IsNew`; internally `ValidateTree()` and held native handles. Non-Windows Program keeps its existing path policy.
- `WindowsPathSecurity.Validate(FileSystemInfo target, bool privateTarget): void`; shared with the Windows branch of `NavalPrivatePath.Check`, preserving its public signature and closed error mapping.
- `WindowsLocalSetup.Ensure(string dataDirectory, string presentationDirectory): LocalSetupResult`; result has `ConfigStore Store`, `Initialized`, `NeedsCredentialPrompt`. This method owns classification and store construction: **no ConfigStore exists before a new root's pending marker**. Preserve public `ConfigStore(string dataDir)` and add internal `ConfigStore(string dataDir, HostConfig initialConfig)` so new-profile config is first written with its final Naval section, after private files, rather than briefly publishing legacy config. `Classify(string dataDirectory): LocalSetupState` returns `Empty`, `Existing`, `Pending`, `Ready`. Missing config in a Ready profile is an incomplete-setup refusal, not permission to recreate it.
- `WindowsLocalAccess.Show(string dataDirectory): bool`; DPAPI load + native dialog; false means cancelled/unavailable, no output of secrets. `WindowsLocalAccessPrompt.Show(string login, string secret): bool` is the narrowly testable native adapter.
- `DesktopBrowser.BuildUri(int port, bool navalEnabled): Uri`; `DesktopBrowser.TryOpen(Uri uri): bool`. Pure URI and launcher seam tests; no public test-only browser override.
- Add `Test-ApexWindowsPublish` to existing `TestEvidence.ps1` for target/runtime evidence checks, not a replacement verifier.
- New `tests/Apex.Windows.Tests` (net8.0, same current xUnit/TestSDK versions as Apex.Tests) is a nonshipped native Windows gate. Source, packaged process, first-run UI/default-shell and CDP browser traits are explicit; no Linux pseudo-pass or silent acceptance skip. Native adapters may be internally injected for source tests only; no CLI/environment simulation authority.

## Smallest coherent implementation brief

Harden Windows private startup before touching config, add empty-root native local-access + build-produced presentation initialization, replace pre-bind Edge launch with post-bind default shell, then extend the existing package/verifier and a dedicated native acceptance project. Reuse all existing UI, producer, passive auth/reader and product tests. Finally run one reviewed source-bound native builder on the authorized feature ref, download/read back the exact artifact, preserve it outside scratch and update the authoritative handoff. Do not reopen completed research/adapters/UI, add an installer or build another release framework.
